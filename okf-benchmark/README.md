# OKF vs. Traditional Routing Benchmark

Tests whether Google's Open Knowledge Format (OKF v0.2) changes matching
accuracy for a real legal case-matching engine, and whether adding extra
"multi-signal" cross-checking on top of it helps further. Full write-up
of what this tests and why: see `docs/` if included, or ask whoever sent
you this package for `OKF_vs_Traditional_RAG_Benchmark.md`.

**This package is self-contained.** `engine_source/` is a full copy of
the real "Legal Case Matcher" prototype (exact → fuzzy → semantic
cascade, 4,260 real Supreme Court cases 2021–2025) that all three arms
run against. Nothing here fabricates or mocks that engine — every arm
imports and runs its actual code unmodified.

## Setup

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
```

First run will download the `all-MiniLM-L6-v2` embedding model
(~90 MB) from Hugging Face — needs internet once, then it's cached.

**Heads up on speed:** the engine pins its embedding threads to 1 for
reproducibility (see `engine_source/src/match/semantic.py`), so
building the semantic index over all 4,260 cases is CPU-bound and slow
on a single core — expect 20–40 minutes per arm for the *first* index
build in a run. This is a one-time cost per arm per process, not
per-document routing time (that's what `bundle_load_ms` / index-build
time in the results measures separately from route latency).

## How to reproduce a full run

```bash
# 1. Build the OKF bundle from the engine's real case pool (~12s)
python producer/build_bundle.py

# 2. Sanity-check the OKF bundle reconstructs the source data exactly
python router/arm2_okf_parity.py
#    → must print "Parity OK" before trusting anything downstream

# 3. Build the test corpus (150 real judgment excerpts, ground truth
#    embedded in filenames, contamination-safe — verification headers
#    are stripped automatically)
python harness/build_corpus.py

# 4. Run each arm (slow — see note above; run one at a time)
python harness/run_benchmark.py --arm 1 --runs 1   # control: engine as-is
python harness/run_benchmark.py --arm 2 --runs 1   # same logic, OKF data
python harness/run_benchmark.py --arm 3 --runs 1   # OKF + multi-signal rules

# 5. Statistical comparison + report
python harness/compare.py
python report/build_report.py
```

Results land in `results/arm{1,2,3}_<timestamp>.json` (one file per
run — `compare.py` and `build_report.py` always pick up the latest per
arm). `report/okf_benchmark_report.html` is self-contained, open it
directly in a browser.

## What each arm actually does

| Arm | Data source | Matching logic | Purpose |
|---|---|---|---|
| 1 — Control | `engine_source/reports/canonical_cases_2021_2026.parquet` (the engine's real database) | The engine's real `CaseMatchingPipeline`, completely unmodified | Baseline |
| 2 — OKF Format Only | OKF bundle in `bundle/matters/` (generated by the producer) | Same unmodified pipeline class as Arm 1 — literally the same Python object, just fed reconstructed data | Isolates the effect of the file format alone |
| 3 — OKF + Multi-Signal | Same OKF bundle as Arm 2 | Arm 2's exact/fuzzy tiers unchanged; semantic tier replaced with top-5 retrieval + re-ranking (judge-name match, filing-year proximity, cross-linked-case graph boost) + a contradiction gate | Tests whether OKF's extra structure, used deliberately, helps |

`router/arm2_okf_parity.py`'s `parity_self_check()` is the load-bearing
check here: it diffs every scalar field and every chunk of case text
between the parquet and the reconstructed OKF bundle, case by case. If
that ever reports mismatches, nothing downstream should be trusted —
it means Arm 2/3 are silently seeing different (probably richer, i.e.
cheating) data than Arm 1.

## Extending this

The obvious next step (flagged as a limitation in our own run) is
sample size: 150 documents, only 30 of them "hard" difficulty, isn't
enough to statistically confirm Arm 3's improvement. `engine_source`
already ships a separate 500-PDF stress-test set
(`reports/demo_test_pdfs/`, with `ground_truth.csv`) that isn't wired
into this harness yet — `harness/build_corpus.py` would need a PDF-text
variant (the engine's own `src/testset/run_pdf_batch_test.py` already
shows exactly how to extract text from those PDFs) to use it instead
of the 150 markdown docs.
